**② 关键产出 —— 上游能力探测矩阵（这一阶段最有价值的产出，直接推翻/改写了多处设计假设）**

非流式：

| 能力组合 | 结果 |
|---|---|
| thinking ON + `tool_choice: required` | ❌ `Thinking mode does not support this tool_choice` |
| thinking ON + `tool_choice: {具体函数}` | ❌ 同上 |
| thinking ON + `tool_choice: auto` | ✅ 返回 tool_calls |
| thinking OFF + `tool_choice: required` | ✅ 返回 tool_calls |
| thinking OFF + `tool_choice: {具体函数}` | ✅ 返回 tool_calls |
| `response_format: json_schema` | ❌ `This response_format type is unavailable now`（两种模式都不行） |
| `response_format: json_object` | ⚠️ 报错要求 prompt 内含 "json" 字样 |

流式时序（同一客服问题，`max_tokens=400`，`stream_options.include_usage`）：

| | 首 reasoning chunk | 首 content chunk | content chunk 数 | reasoning_tokens |
|---|---|---|---|---|
| thinking ON | 0.76s | **从未出现** | **0** | 400（烧光全部预算） |
| thinking OFF | 无 | 0.55s | 400 | 无 |

关闭 thinking 的有效开关（探测到两个）：`"thinking":{"type":"disabled"}`、`"reasoning_effort":"none"`。
无效的：`"enable_thinking":false`、`"chat_template_kwargs":{"thinking":false}`（这两个实测仍会产生 reasoning_tokens）。

上游 `/models` 实际目录（2026-09-18）：`deepseek-flash`、`deepseek-v4-pro`。

Context7 查证结果（langchain 1.4.1 / langchain-core 1.6.3 / langchain-openai 1.6.2）：

- `ChatOpenAI(base_url=, api_key=, model=)` 支持自定义端点
- `with_structured_output` 的**默认 method 即 `function_calling`**，正好是上游唯一可行路径
- `trim_messages` / `count_tokens_approximately` 位于 `langchain_core.messages.utils`（**不是** `langchain_core.messages`）
- `ChatPromptTemplate.from_messages([("system", ...), MessagesPlaceholder("history")])` 形态成立
- 1.x 流式取文本用 `chunk.text`，**不是** 0.x 的 `chunk.content`

**② 关键产出**

- **Spec**：`docs/superpowers/specs/2026-09-18-ecom-customer-service-chat-design.md`
- 12 节结构，其中 §3「上游能力实测结论」为全文经验基础，§12 记录 5 项未决/风险（2 项标为**阻塞性**）
- 关键设计决策及其理由：
  1. **薄分层、不用 LCEL 管道** —— 上游三处非标约束（thinking、tool_choice、json_schema）让标准管道变成负担
  2. **`chat.py` 出领域事件，`api.py` 只封 SSE 帧** —— 对话逻辑可脱离 HTTP 单测
  3. **`APP_LLM_EXTRA_BODY` JSON 字符串透传** —— 避免把 DeepSeek 特有的 `thinking` 参数硬编码，换 provider 只改 `.env`
  4. **`start_on="human"`** —— 防止剪裁出「回答还在、提问没了」的孤儿消息
  5. **`meta` 事件承载 session_id** 而非响应头 —— curl 免 `-i`
  6. **断线不写入半截 assistant 历史** —— 否则污染下一轮上下文
- Spec 自查发现并**当场修复**一处：§4.1 只画了 `app/` 目录，但 §10/§11 引用了 `evals/` 和 `scripts/`，仓库根布局缺失；同时补上 uv 依赖管理与已验证的 Python 3.14.4 兼容结论
- 新增 `.gitignore`（首要目的是防止 `.env` 里的 key 进仓库）

- **计划对 spec 的两处修正**（已同步回 spec）：
  1. `APP_SESSION_MAX_TURNS` 拆成 `APP_SESSION_MAX_SESSIONS` + `APP_SESSION_MAX_MESSAGES`。原设计用单个"轮次上限"防内存增长，但**只限会话数并不阻止单个会话无限增长**——这是 spec 里的一个真实漏洞，写计划时才暴露
  2. 新增 spec §7.2.1「一轮对话的原子性」：`prepare_messages()` 的输入**不含**当前消息，当前消息由函数内部无条件追加。原设计若把当前消息一起丢进剪裁器，预算极小时会把用户提问本身剪掉 → 模型收到空提问
- Plan 自查覆盖表：spec 全部 18 个小节均映射到任务；无占位符；跨任务签名一致性逐条核对通过
