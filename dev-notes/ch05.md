## 阶段 0 · 需求与设计定稿（2026-10-21）

**① 关键原话**

> 我要用 Superpowers 模式把客服系统升级成生产级架构:Workflow 确定性编排做骨架,主力 Agent 作为骨架里的核心节点。
>
> （订单号缺失逻辑）独立节点，物流/订单/售后都拦
>
> （会话记忆归属）A：checkpointer 为准，MySQL 审计（推荐）

**② 关键产出**

- **Spec**：`docs/superpowers/specs/2026-10-21-langgraph-workflow-design.md`
  - 图骨架：sanitize → begin_turn → 指代消解 → 意图识别 → 硬编码分流 → 知识检索/插槽门/投诉/闲聊 → 置信度闸 → ReAct 子图 → 日志。
  - 7 类意图 → 4 出口的映射表写死在代码里。
  - 订单号插槽门覆盖物流/订单/售后，等待态跨轮由 State 承载。
  - 置信度闸最简版：有重排分用 `top_score`，否则用查询字符二元组覆盖率（阈值 0.30）。
  - Checkpointer：官方 `AsyncSqliteSaver`，`thread_id=session_id`；模型上下文以 State.messages 为准，MySQL 只做审计（方案 A）。
  - 前端：`done.actions` 下发按钮；转人工纯前端；建工单走 `POST /api/tickets` 确定性调用第 2 章工具。
  - 裸循环热身脚本 `scripts/bare_agent_loop.py` 保留为教学/诊断工具。
- **Context7 查证**：LangGraph `astream(stream_mode="custom", subgraphs=True)` + `StreamWriter` 的用法；官方 checkpointer 只有 SQLite/Postgres（无官方 MySQL）。
- **依赖解析**：`uv pip install --dry-run` → `langgraph==1.2.16`、`langgraph-checkpoint-sqlite==3.1.2`，与现有 langchain-core 1.6.3 共存。

**③ 被拒绝或纠偏**

- Builder-check 提了 8 个问题，逐条裁定（spec §15）：
  1. 失败轮悬空 tool_calls → 图入口 `sanitize_messages`，失败轮不写审计。
  2. 等待态用户换问题 → 由 `classify_intent` 判断消息是否匹配订单号，匹配沿用原意图、不匹配则清空等待态重新分类；图不加回边。
  3. State 跨轮残留 → `begin_turn` 重置 turn 级字段；`node_trace` 改覆盖式列表。
  4. ch04 的 `<INSUFFICIENT_KNOWLEDGE>` 保留，仍在 API 流式适配层处理。
  5. `retrieve` 必须显式传 `strategy`/`session_id`；已有 `refusal_reason` 时闸门不重复入池。
  6. 知识类工具集移除 `query_faq`，避免预检索证据与工具引用两套编号打架；业务类保留五工具。
  7. 审计写完整 ReAct 序列，`evidence` 注入消息不落库。
  8. 动作只在 `done.actions`；工单类型按路由映射（知识→咨询/业务→售后/投诉→投诉）。
- 被否的备选：订单号逻辑放工具内（要改第 2 章工具）、`interrupt` 追问（前端恢复协议过重）、ReAct 写成单节点 while（不落每步 checkpoint）。

**④ 翻车与返工**

- 无（设计阶段）。待用户确认 spec 后进入 writing-plans。
