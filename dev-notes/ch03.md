**② 关键产出 — 实测数据（这一阶段最有价值的部分）**

**Embedding 上游实测**：`BAAI/bge-m3`，HTTP 200，约 0.84s，**1024 维**，OpenAI 标准响应形状。

**★ 第一次召回测试：失败。** 用 ch02 那 12 条短问答当知识库：

```
「邮费是多少」
  0.5853  发什么快递        ← 错的排第一
  0.5651  换货运费谁承担    ← 该召回的排第二
```

原因：`换货运费谁承担` 的答案里只有"运费"、从不出现"邮费"，而"发什么快递"与"邮费"共享物流配送语义。

**★ 第二次：用贴近真实手册的 chunk → 通过。**

```
「邮费是多少」  0.6376  运费说明  ← ✅ top1，领先 0.069
「退货政策是什么」0.6989 退货政策
「怎么开发票」   0.7502 怎么开发票
「什么时候发货」 0.7540 发货时效
```

**★ 查询形态对领先幅度的影响**：

| 查询形态 | top1 | 领先 |
|---|---|---|
| 2 字「邮费」 | 0.6350 | +0.0504 |
| 4 字「退货运费」 | 0.7874 | +0.1345 |
| 完整问句「邮费是多少」 | 0.6376 | +0.0691 |
| 口语「退货要自己出邮费吗」 | 0.7015 | +0.0822 |

→ 四种都能排对，但 2 字核心词的领先只有约一半。这是改 `query_faq` docstring 的直接依据（旧文档写着"不要传整句话"，在向量检索下是**反向指引**）。

**★ 共存验证：12 条短 FAQ + 手册 chunk 同时入库（14 条）**：

```
「邮费是多少」  0.6377  运费说明[MD]   ← ✅ 仍排第一（短 FAQ 只是占位）
「运费怎么算」  0.6823  运费说明[MD]   ← ✅ 仍排第一
```

→ 「把 12 条 FAQ 作为来源之一导入」这个决策**不破坏验收 1**。

**pymilvus vs langchain-milvus 的 Context7 查证结论**：

- `pymilvus`：`MilvusClient` + `create_schema(auto_id=False)` + `add_field` + `upsert(collection, data)`（**按主键幂等**）+ `search(..., limit, output_fields)`
- `langchain-milvus`：`Milvus(embedding_function=..., auto_id=True)` + `add_documents(...)` + `similarity_search(...)`；**官方文档示例走 `auto_id=True`，重跑会重复插入**
- **裁决依据**：本章验收 2 依赖按主键幂等，而这正好落在 langchain-milvus 封装掉的那一层 → 选 pymilvus 直连

**④ 翻车与返工 —— 自查抓到三处真缺陷，全部就地修掉**

1. **`dedupe_and_import` 原打算把 `content_hash` 留空**，指望随后的 `build_knowledge` 补上。**但 dedupe 会把 staging 行标成「已入库」，而 `load_mined_chunks` 只读「待入库」——那条补 hash 的链路根本走不到**，hash 会永久是空串，之后的内容变化检测全部失效。改为在 dedupe 时就构造成 `Chunk` 并取 `chunk.content_hash`。
2. **Task 7 的 builder 测试原本用 `db_session`**，而 `build` 为了真实的重跑语义必须 `commit()`；`db_session` 是"跑完回滚"的，commit 会让回滚失效、把测试数据留在库里，**干扰 `test_knowledge_repo` 的计数断言**。改为独立 session + 唯一 id 前缀 + 事后只删自己造的行；`test_counts` 同时改成增量断言，不再依赖绝对条数。
3. Task 10 的测试导入写错了模块名（`app.jobs_helpers`），改为 `app.knowledge.dedupe`。

**教训**：前两条都不是笔误，是**状态机与测试夹具的语义冲突**——一处是"谁负责算 hash"，一处是"谁拥有事务边界"。这类问题在写代码时很难在单点看出来，必须在计划阶段把数据流从头到尾走一遍。

|---|---|---|
| 裸字符串 | **0.635** | 运费说明 top1 |
