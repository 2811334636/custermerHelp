## 阶段 0 · 启动与现场勘察（2026-09-20）

**① 关键原话**

> 我要用 Superpowers 模式给现有的客服系统装上查数据的能力,用 Function Calling 让模型自己决定调什么工具——工具链要长在客服聊天本身,用户在聊天页问一句就能触发。
> 功能需求：FastAPI+SQLAlchemy 分层骨架 / Docker 起 MySQL / 四张表 / 五个 @tool 工具 / 工具基础设施（注册、Schema 校验、错误处理、超时重试）/ 工具链并入现有 SSE 聊天流 / 聊天页工具徽章 / 只做单轮调用
> 技术栈：FastAPI + SQLAlchemy + MySQL(Docker)、LangChain @tool
> 本章不做：多轮自动循环的 Agent Loop、向量检索/RAG
> 验收：① 聊天页问「订单 1001 的物流到哪了」看到工具徽章并按结果作答 ② 「退货政策是什么」query_faq 查得到 ③ 「邮费是多少」查不到——这个漏召回是预期结果,记下来留给下一步升级

**② 关键产出**

- **Spec**：`docs/superpowers/specs/2026-09-20-ecom-tool-calling-design.md`，15 节
- 核心设计决策及其理由：
  1. **四层切分**（`db/` → `repositories/` → `tools/` → `chat.py`），边界判据是"这一层知道什么"
  2. **工具轮用流式探测**（判第一个增量是正文还是工具申请），不用非流式——否则每轮对话都退化成假流式，把 ch01 的验收标准 1 弄丢
  3. **第二次模型调用不绑工具** —— 单轮收敛是**调用方式本身决定的**，不是靠计数器拦出来的
  4. **"查不到"不是错误，"坏了"才是** —— 业务空结果是正常返回，异常只留给真故障
  5. **假数据确定性生成**（`_rng(key)`）—— 否则验收标准 1 无法对账，退化成"看着像对"
  6. **`create_ticket` 的会话 id 由上下文注入，不在工具签名里** —— 模型不该能指定往哪个会话建单
  7. **工具中文标签放前端** —— 后端发 `label` 会把 UI 词汇渗进领域事件
  8. **faq 种子数据故意不含「邮费」** —— 这是验收 3 要暴露的问题，不是遗漏

**③ 被拒绝或纠偏**

- **★ 用户驳回了一次我的提问，而且是对的。** 我问"`create_ticket` 建单后要不要把会话状态改成「已转人工」"，用户反问："为什么说,如果不改,这个字段可能会没有人写?这难道不只是对当前会话的状态做一个标记吗"
  - **我的提问方式是错的**：我把一个**字段语义本身决定的行为**（状态标记就该在状态变化时更新）包装成了 A/B 权衡。`conversations.status` 的含义就是"这通会话处于什么状态"，建了工单就意味着转人工了——这不是权衡，是定义。
  - 我当时顾虑的"写操作从一张表变两张表，职责不单一"**站不住**：`create_ticket` 这个业务动作的语义就是"转人工"，写两张表正是在如实表达这个语义。表数量不是职责边界的判据。
  - **已定为**：`create_ticket` 成功写 tickets 后，在同一事务内把会话 status 改为「已转人工」。
  - 顺带纠正我自己的措辞：「已结束」这个值在本章确实没有触发它的动作（本章没有"结束会话"操作），但这不是"字段没人写"，是**那一章还没做**。

**④ 翻车与返工**

- **Spec 自查抓出四处需要补**，其中一处是真实缺口：
  1. **★ `conversations.user_id` 是 `NOT NULL` 但没有数据来源** —— ch01 的 `ChatRequest` 只有 `session_id` + `message`，本章也不做鉴权。不补这一列的话插入直接失败。**定为**：固定写 `'anonymous'`，并提为配置项 `APP_DEFAULT_USER_ID`；副作用（索引无区分度）记入已知限制。
  2. `query_faq` 检索哪一列未明确 —— **定为只搜 `question`**。若连 `answer` 一起搜，某条答案里顺带提到"邮费自理"就会命中，会让验收 3 的结论依赖种子数据的措辞巧合，测的就不是检索能力而是数据运气。
  3. 测试库谁建未明确 —— 定为 `seed.py` 负责创建 `customer_service_test` 并执行同一份 `schema.sql`，保证表结构只有一份真相。

## 阶段 2 · 写实施计划时被实测推翻两处设计（2026-09-20）

**① 关键原话**

> 就按照这个该,对于那个prompt,应该允许调用工具,按照你说的来

**② 关键产出**

- **Plan**：`docs/superpowers/plans/2026-09-20-ecom-tool-calling.md`，**12 个任务**
- 依赖解析（沙箱内实测）：SQLAlchemy **2.0.54** / aiomysql **0.3.2** / pymysql 1.2.3 / greenlet 3.5.6
- Context7 查证：SQLAlchemy 2.0 异步形态（`create_async_engine` / `async_sessionmaker(expire_on_commit=False)` / `Mapped`+`mapped_column`）；LangChain 流式下 tool_calls 靠 **`gathered = chunk if gathered is None else gathered + chunk`** 累积（官方文档确认）

**★ 写计划时的"先实测再写"救了两处设计**（这是 ch01 那次教训的直接复用——ch01 的三个上游坑全是实测出来的）：

### 发现 A：流式下"先正文后工具"是**正常行为**，不是边界

计划初稿把工具轮设计成"看模型吐的第一个非空增量——是正文就判定不需要工具"。实测（**无 System Prompt**）：

```
chunk2: content='I'   tool_call_chunks=[]
chunk3: content="'ll" tool_call_chunks=[]
...
第一个非空增量的类型: text                              ← 按原设计会判定"不需要工具"
累积后 tool_calls = [{'name': 'query_logistics', ...}]  ← 但模型明明要调工具
```

**按原设计，用户会看到机器人说"我去查一下"，然后工具不执行、没有下文。** 而我把这种情况写在 spec §7.6 当"几乎不会发生的边界，不加逻辑（YAGNI）"——**它不是边界，是模型的正常行为。**

**返工**：设计改为「**先转发后决断**」——正文一律实时转发并累积，**流结束后**看最终 `tool_calls` 是否为决定走向。好处是不再依赖任何未经证实的假设；不需要工具时仍是真流式。

### 发现 B（更严重）：**ch01 的 System Prompt 与 ch02 的功能直接冲突**

带 ch01 的真实 System Prompt 再测：

| 提问 | 第一个增量 | 结果 |
|---|---|---|
| 订单 1001 的物流到哪了 | TEXT | **没调工具**，模型说"抱歉，我这边看不到订单的物流信息，没法帮您查" |
| 退货政策是什么 | TOOL_CHUNK | ✅ 调了 `query_faq` |
| 你好 / 谢谢 | TEXT | ✅ 不调工具 |

**根因**：ch01 的 System Prompt 写着「你**没有**订单系统的访问权限…你**绝对不能**说'我帮您查到了'」。模型老实遵守了，于是**拒绝查物流**——**验收标准 1 在不改 Prompt 的情况下 100% 会失败**。

**这是 spec 里完全漏掉的一块交付物**：设计阶段全程盯着工具、数据库、SSE，**没检查既有 Prompt 会不会与新能力打架**。

**返工**：新增 Task 8「改写 System Prompt + 工具选择评估集」。改法是把"你没有权限"改成"你可以通过工具查，但**只能转述工具返回的内容**，不得补充/推测/编造"——保住原约束的真正意图（不许凭空断言订单事实），解除与新能力的冲突。

**并当场实测了新 Prompt**（8 个场景）：**工具选择 7/8**

| 场景 | 结果 |
|---|---|
| 物流/订单详情/FAQ命中/转人工 | ✅ 都调对了工具 |
| 你好 / 谢谢 / 帮我写 Python 脚本 | ✅ 都不调工具 |
| **邮费是多少** | ❌ **不调，反问了**："您指的是哪方面的邮费呢？" |

### 发现 C（连带）：验收标准 3 的原始措辞触发不了工具

「邮费是多少」模型会反问澄清。继续实测几种说法：

| 措辞 | 是否调 `query_faq` |
|---|---|
| 邮费是多少 | ❌ 反问 |
| **邮费政策是什么** | ✅ 调 |
| 你们收邮费吗 | ✅ 调 |
| 运费怎么算 | ✅ 调 |

**验收标准 3 的措辞已按实测改为「邮费政策是什么」**——这不是把用例改到能过，而是选定**能触发工具**的措辞，才能暴露要记录的漏召回（faq 表里确实没有「邮费」条目）。

**★ 环境三处偏离（都用实测证据说服了我）**

1. **3306 被占，容器改映射 3307** —— 宿主 3306 被 Windows 侧 MySQL80 + VMware NAT 占用，绑 `0.0.0.0:3306` 与 `127.0.0.1:3306` 均失败。**用户随后主动确认了这一点。**

3. **新增 `scripts/init-test-db.sql`** —— 官方 entrypoint 只给 `app` 授权 `MYSQL_DATABASE`，测试库需显式建库+授权。

### ② ★ 真机跑出来的一个 bug：`🔧 undefined`

任务简报里贴的那份 HTML，在读 `phase=end` 时用的是 `data.name`。但**后端 end 帧不带 name**
（`app/api.py:110-114` 只发 `call_id` / `ok` / `summary` / `elapsed_ms`）。于是徽章渲染成
`🔧 undefined · 订单 1001 的物流信息：…`——工具名丢了。

修法在前端：start 帧把 `call_id -> {元素, name}` 存下来，end 帧按 `call_id` 取回名字。
没动后端，也没给 end 帧加 name——**两帧分工本来就该是 start 声明"谁"、end 声明"结果如何"**，
end 帧重复发 name 是冗余。（简报的示例代码是这里唯一的错，SSE 契约本身与 Task 10 一致。）

顺带加的兜底：万一没收到 start 帧（例如将来有人改成只发 end），退回用 `data.name`，不至于整块徽章消失。
